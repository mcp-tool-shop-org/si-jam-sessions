# Lane 5 — reproducible audio pipelines (Opus research seat, 2026-09-25; retrieval claimed, NOT yet gated)

Not retrieved: RFC 6716 §6 conformance (fetches cut off; a summariser invented a "MUST be bit-exact" line — discarded); nnAudio vs librosa numbers (PDF > 10 MB); any ffmpeg-vs-libsndfile decoding vs model accuracy study (none found). PDFs read via r.jina.ai where they would not parse.

1. Raffel, McFee, Humphrey, Salamon, Nieto, Liang, Ellis 2014, mir_eval, ISMIR, https://archives.ismir.net/ismir2014/paper/000320.pdf — vs existing (mostly MIREX) implementations, average relative change up to 11.08% (NCE-under), 10.10% (voicing false alarm), 9.17% (information gain) (body Table 2); causes = conventions (undefined case scored 1 vs 0, histogram binning, greedy vs optimal matching). → pin the evaluator in the law and document undefined-case handling.
2. Bittner, Fuentes, Rubinstein, Jansson, Choi, Kell 2019, mirdata, ISMIR, https://archives.ismir.net/ismir2019/paper/000009.pdf — one of four copies of the Beatles set failed checksum on every audio file; iKala has three hop sizes in circulation (0.032, 0.03125, 0.032017 s) with significant metric differences; every public iKala loader read f0 wrongly (body). → checksum manifest + reference loader; time as integer samples + integer rate.
3. Urbano, Bogdanov, Herrera, Gómez, Serra 2014, ISMIR, doi:10.5281/zenodo.1416276 — mean MFCC error vs lossless ~6.1–6.7%, levelling ~3% (Essentia, 256 kbps) / ~5% (QM Vamp, 160–192 kbps) (body). → labels on lossless PCM only.
4. PyTorch, torchaudio 0.11.0 "Audio Resampling" tutorial, https://docs.pytorch.org/audio/0.11.0/tutorials/audio_resampling_tutorial.html — configured to mimic librosa kaiser_best/kaiser_fast, outputs still differ by MSE 2.08e-6 / 2.52e-5 (RMS ~1.4e-3 / ~5.0e-3, seat's arithmetic) (body, printed output). → a resampler is an algorithm choice; any resampling inside CQT/YIN belongs to the pinned law.
5. Gladman, Innocente, Mather, Ozaki, Zimmermann, Aug 2026, "Accuracy of Mathematical Functions in Single, Double, Double Extended, and Quadruple Precision", HAL hal-03141101, https://members.loria.fr/PZimmermann/papers/accuracy.pdf — GNU libc 2.44 largest known double errors: sin 0.516 ulp, pow 0.523, cbrt 3.67 (Table 3); LLVM libc 22.1.8 functions seem correctly rounded except atan, atan2, pow; IEEE 754-2019 only recommends correct rounding; one library can differ across CPUs by run-time FMA/AVX dispatch (body). → law code never calls the host libm.
6. Inria, CORE-MATH project page, https://core-math.gitlabpages.inria.fr/ — MIT-licensed correctly rounded functions for every rounding mode; float32 single-argument checked exhaustively, double only against known hard cases; shipped in GNU libc 2.42+ and AMD libm 4.2+; Rust libm's cbrt is a 2025 port (https://github.com/rust-lang/compiler-builtins/blob/master/libm/src/math/cbrt.rs); core-math crate 1.3.0 wraps the C sources (https://docs.rs/core-math). → port the synth's few functions to pure Rust from CORE-MATH; a correctly rounded result is unique, so any correct implementation gives the same bits (inference).
7. Subnormals — WebAssembly Core Spec numerics (https://webassembly.github.io/spec/core/exec/numerics.html): deviations from IEEE 754 are only round-to-nearest-even, optional NaN payload propagation, non-stop mode — none allows FTZ, so scalar subnormals are exact (inference). Arm NEON Programmer's Guide DEN0018A (https://developer.arm.com/documentation/den0018/a/NEON-Instruction-Set-Architecture/Flush-to-zero-mode): ARMv7 NEON always flushes to zero. Intel oneMKL guide 2023.0 (https://www.intel.com/content/www/us/en/docs/onemkl/developer-guide-linux/2023-0/operating-on-denormals.html): denormals via slower software assist. de Soras 2002 (https://www.musicdsp.org/en/latest/_downloads/d81fc9af8a9fa63332b248772fbb4a54/denormal.pdf): ~170 cycles per denormal multiply on AMD Thunderbird, >30× slower; IIR feedback and delay lines produce them (body). LLVM issue #57589 (2022, https://github.com/llvm/llvm-project/issues/57589): loading a shared library built with -ffast-math turns FTZ on process-wide. → zero tiny feedback state by explicit comparison, never an FP mode flag; a decaying IIR tail in the golden corpus.
8. van Beurden & Weaver 2024, RFC 9639 FLAC, https://www.rfc-editor.org/rfc/rfc9639.html — MD5 over all samples, interleaved, signed, little-endian, sign-extended to whole bytes; independent of compression level and container. FFmpeg CRC muxer (https://ffmpeg.org/ffmpeg-formats.html) converts to s16 before checksumming by default. → content-address the samples, not the files.
9. Lossy decoders held to tolerance — Underbit summary of ISO/IEC 11172-4 (https://www.underbit.com/resources/mpeg/audio/compliance): full-accuracy MP3 decoder < 2^-15/√12 RMS and 2^-14 max error re full scale (page body). FFmpeg FATE mp3.mak / aac.mak: max sample difference tolerances 18 and 2, not exact diff. Opus opus_compare.c (https://github.com/xiph/opus/blob/main/src/opus_compare.c) and RFC 8251 (Valin & Vos 2017): compliant = passes test vectors under a Bark-weighted quality Q ≥ 0. LAME Technical FAQ (Taylor 2000, https://lame.sourceforge.io/tech-FAQ.txt): decoder adds 528 samples, encode+decode round trip 1056. → lossy = previews only; onsets on lossy copies shift ~24 ms at 44.1 kHz (seat's arithmetic).

Recommendation (seat): stored fact = 24-bit integer PCM quantised by the pinned wasm law under a specified rule, stored as FLAC, identified by SHA-256 over FLAC-style sample bytes; labels from stored PCM (int→f64 exact) at declared integer resolution (onsets in samples, pitch in millicents), with the law binary hash. Bit-exact: PCM, hash, law-derived labels on every JS engine and CPU. Tolerance-bounded: librosa/Essentia/mir_eval cross-checks, native builds, lossy previews. Tolerance per label unit = max(one step of the stored format — RMS ≤ q/√12, max ≤ 2q; at 16 bits exactly the ISO MP3 full-accuracy rule — , the spread between independent reference implementations on the golden corpus); exceeding it halts release.
